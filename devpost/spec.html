How this works, in plain language

The browser handles the form and keeps the current brief/results in memory. A small server route validates the brief, adds the private OpenRouter key, requests structured JSON, checks it, and returns it to the browser to display.

Why this shape

No separate backend, account system, or database is needed for the demo. That keeps setup and cost down; refreshing the page clears the current brief and results.

One important boundary

The OpenRouter key stays in the server environment. It never goes into browser code, a NEXT_PUBLIC_ variable, or a Git commit. User-entered brief details are sent to OpenRouter to generate content and are not saved by this app. Visitors should not enter confidential information or customer personal data.

One stable result shape

OpenRouter Structured Outputs uses a JSON Schema for predictable display. The server checks the parsed response with Zod and checks cross-field rules such as selected-platform matching and exactly seven ascending days.

Social content

Exactly one object for each selected platform. Each contains a platform, promotional headline, caption, useful hashtags (possibly an empty list), and CTA. Every MarketingResult field is required; only MarketingBrief.offer is optional (unless the special-offer goal is chosen).

socialContent[] platform: instagram | facebook headline: string caption: string hashtags: string[] callToAction: string

Shared seven-day plan

One plan coordinates the selected platforms. Show the campaign summary as its objective. Each day has an idea, format, caption per selected platform, CTA, and a suggested tracking metric.

campaignPlan[7] day: 1..7 contentIdea: string format: string captions[]: { platform, caption } callToAction: string suggestedMetric: string

Business brief sent to the route

POST /api/generate { "brief": { "businessName": "Daily Grind Coffee", "productOrService": "Iced coffee and matcha latte", "targetAudience": "College students and young professionals", "marketingGoal": "special_offer", "platforms": ["instagram", "facebook"], "brandTone": "friendly", "offer": "10% off selected drinks this weekend" } }

Response success: { "result": MarketingResult }. Failure: { "error": { "code", "message", "retryable" } }.

Quality boundary: the prompt must follow the audience, goal, tone and offer, and avoid made-up prices, facts, guarantees or performance. Schema validation guarantees shape, not truth or effectiveness; one real sample gets a human content review.

Errors and recovery

Failures return a small safe contract. The UI never loses the user’s brief or erases previous successful results during a failed regeneration.

FailureServer behaviorWhat user can do
Invalid fields / body too large400, no provider callFix inline errors; inputs remain
Missing API key503, no retrySee configuration unavailable message
Rate limit429; no automatic retryWait, then Retry or edit brief
Network, timeout, provider 5xxAt most one transient server retryPlain error with manual retry
Refusal, incomplete or invalid outputSafe normalized 422/502Retry or edit; raw provider data hidden

The SDK’s automatic retries will be disabled so the app owns a single clear retry budget. A timeout retry might duplicate upstream work; no retry loop is allowed. The browser treats any HTTP 429 as a rate-limit state, even if the WAF returns a different body shape.

Protection

Request/body caps and Vercel WAF fixed-window source-IP limit for the public generate route.

WAF docs and pricing

Anonymous public-demo safeguard

Initial recommendation: 10 requests per 10 minutes per IP on POST /api/generate, returning the default 429 after the threshold. This is one layer, not a global spend cap: several IPs can each call the endpoint, while visitors sharing one IP count together. Monitor OpenRouter usage. If traffic or spend is unexpected, set GENERATION_ENABLED=false in Vercel and redeploy to disable generation. Hobby supports a single fixed-window WAF rate-limit rule; Vercel’s current page lists 1 million allowed requests included for Hobby, then $0.50 per additional million and asks the account owner to review pricing while creating the first rule. Confirm dashboard terms/pricing before publishing. Also limit brief fields and request body to 8 KB; limit model output size.

Start with OPENROUTER_MODEL=openai/gpt-6-luna, reasoning.effort=low, and max_output_tokens=5000; check the values with the first real generation. OpenRouter pricing and limits depend on the selected model; verify current details before a public launch. Vercel Hobby is restricted to personal or non-commercial use in current terms. Its current terms also say it may use content submitted under Hobby for model training, so use non-sensitive demo inputs and review the plan/privacy terms before real business use.

Where it runs and how to try it

Build and verify locally first, then deploy through Vercel’s web interface. A public live URL adds convenience for reviewers but does not replace the demo video or public source repository.

Local

  1. Install Node.js 20.9+ and npm.
  2. Set OPENROUTER_API_KEY in the ignored root .env.local.
  3. Run npm install, then npm run dev.
  4. Open http://localhost:3000.
  5. Run mocked tests with npm run test.

Public demo

  1. Import the public GitHub repository into Vercel.
  2. Set the server-only OPENROUTER_API_KEY in Vercel project settings.
  3. Deploy; configure/publish the WAF rule and review its current pricing prompt.
  4. Test one live generation and safe 429/error handling.
  5. Prepare a public demo video under three minutes; check event rules and add an open-source license to the public repo.
Plan and privacy note: this demo is intended for non-commercial hackathon evaluation. Use non-sensitive sample inputs on Hobby and recheck Vercel’s current terms before using real business information or running commercially. The app’s form notice should tell visitors the brief is sent to OpenRouter, is not saved by the app, and should not contain confidential or customer personal data.

Testing without routine API spend

Vitest proves app rules with mocked AI responses. One or two real API runs check that provider configuration and generated content work together.

Automated (mocked)

  • Required fields and conditional offer validation.
  • Output shape, exact seven days and selected platform matching.
  • Prompt rules against invented business claims.
  • Provider failure mapping and API route behavior.
  • No normal test makes an OpenRouter request.

Manual / live

  • Sample coffee shop; Instagram only, Facebook only, and both.
  • Copy, edit/regenerate, mobile layout and keyboard errors.
  • Simulate failure and confirm form/prior result survive.
  • One local real generation; second only to diagnose a problem.
  • After deploy, verify one live generation and safe failure path.

Review notes

This blueprint is sized for the hackathon prototype and gives every approved PRD behavior a code home.

  • The single brief clearly feeds one server-side model call and two coordinated UI outputs.
  • The stack builds on the learner’s Next.js/React/Tailwind experience; the separate API service and database are avoided.
  • Every form, result, copy, loading, retry, and mobile requirement maps to named components and tests.
  • The main operational checkpoint is setting the OpenRouter key and reviewing/publishing Vercel’s WAF rule before exposing live generation.
